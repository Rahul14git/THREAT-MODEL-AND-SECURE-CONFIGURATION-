Threat model and hardening plan: Crumb & Co. pre-order app

A small bakery’s website where customers order cakes and pick a pickup slot, and the baker manages orders. I used STRIDE to find threats, scored each by likelihood × impact (1–5 each), and turned the results into a verifiable hardening checklist.

1. Scope and assumptions

  • System: a single web app (React front end, Node/Express API, PostgreSQL) on a cloud host, with an object store for reference photos.
  • Users: anonymous visitors, registered customers, and one to three admin staff (the baker, a helper).
  • Third parties: Stripe (card payments, never touches our servers directly) and an email provider (order confirmations).
  • Out of scope: physical security of the shop, the staff’s personal devices, and the cloud provider’s own infrastructure.
  • Attackers considered: opportunistic bots and credential stuffers, a curious or malicious customer, and a competitor or disgruntled ex-staff member. Not considered: nation-state actors.

2. Assets worth protecting

Customer PIINames, emails, phone numbers, addresses, allergy notes. Leak means privacy harm and legal exposure.
Admin accountsFull control of orders, prices, refunds. The highest-value target.
Payment integrityOrders must only be marked paid when Stripe confirms. Card data stays with Stripe.
SecretsStripe keys, webhook secret, DB password, email API key.
AvailabilityPickup slots and the site itself. A weekend outage means lost revenue.
ReputationWrong allergy info or fake orders harm trust and can harm people.

4. Threats (STRIDE) and risk ranking

Why this order? Admin takeover (T1) and cross-customer data exposure (T2) hurt the most people with the least attacker effort. Injection and leaked secrets (T3, T4) are rarer but catastrophic. Business-logic issues (T5, T6) cost money directly and are cheap to fix, so they follow immediately.

5. Prioritized hardening plan with verification

Each item names the threat it addresses and a concrete check that proves the fix works. Do phase 1 first.

Phase 1: Critical (do now)

  • Require MFA for admins, add login rate limiting and lockout; hash passwords with Argon2id or bcrypt. (T1)Verify: 10 wrong passwords in a minute returns HTTP 429; an admin account without MFA cannot reach /admin; check the DB stores no plaintext hashes like MD5.
  • Enforce object-level authorization on every order and profile endpoint; use unguessable IDs (UUIDs). (T2)Verify: an automated test logs in as customer A and requests customer B’s order and expects 403 or 404. Add this test to CI.
  • Use parameterized queries or an ORM everywhere; validate input types and lengths. (T3)Verify: searching ' OR '1'='1 returns no extra rows; search the code for string-concatenated SQL; run OWASP ZAP’s active scan against staging with zero injection findings.
  • Move secrets to environment variables or a secrets manager; rotate anything ever committed; turn off debug errors in production. (T4)Verify: run gitleaks detect across full git history with no findings; trigger an error and confirm the response is generic with no stack trace.

Phase 2: High (this month)

  • Recalculate price and totals on the server from the product catalog; ignore client-sent amounts. (T5)Verify: intercept the checkout request with a proxy, change the price, and confirm the server charges the catalog price.
  • Verify the Stripe webhook signature and check the amount and order ID before marking paid. (T6)Verify: a curl POST to the webhook URL with no or a wrong signature returns 400 and the order stays unpaid.
  • Escape all output, sanitize notes, and set a strict Content-Security-Policy; mark cookies HttpOnly, Secure, SameSite=Lax. (T7)Verify: submit <img src=x onerror=alert(1)> as a note and confirm it displays as text in the admin view; check cookie flags in browser dev tools.
  • Add rate limits and CAPTCHA to checkout and slot booking; cap emails per address per hour; hold unpaid slots for 10 minutes only. (T8)Verify: a script making 50 orders from one IP is throttled; unpaid reservations release automatically.
  • Enable Dependabot or npm audit in CI, commit the lockfile, and block merges on high-severity findings. (T9)Verify: CI fails when a known-vulnerable package version is introduced on a test branch.

Phase 3: Medium (next quarter)

  • Place the DB in a private network with no public IP; encrypt backups and restrict who can read them. (T10)Verify: a port scan of the DB host from outside shows 5432 closed; perform a test restore from backup and confirm access is limited to named roles.
  • Make the photo bucket private and serve files through short-lived signed URLs. (T11)Verify: opening an object URL without a signature returns 403.
  • Write an append-only audit log for logins, refunds, price changes, and role changes, including user ID and time. (T12)Verify: perform a test refund and find one log line with who, what, and when; confirm admins cannot edit log entries.
  • Validate uploads by real file type and size, re-encode images, and store them outside the web root with random names. (T13)Verify: uploading a .php or renamed .exe file is rejected; a 50 MB file is refused.

Baseline secure configuration (quick wins)

  • HTTPS only with HSTS; set X-Content-Type-Options, Referrer-Policy, and frame-ancestors in CSP.Verify: curl -I https://yoursite shows the headers; an SSL Labs or Mozilla Observatory scan grades A or higher.
  • Least-privilege DB user for the app (no DROP or superuser rights); separate staging and production credentials.Verify: connect as the app user and confirm DROP TABLE fails.
  • Alert on spikes in failed logins, 5xx errors, and Stripe webhook failures.Verify: simulate each event and confirm an alert reaches the owner.

6. Short explanation

I started by deciding what an attacker would actually want from a small bakery app: admin access, other customers’ personal details, and free cakes. I drew the system with three trust boundaries and nine data flows, then walked each flow through the six STRIDE categories to find abuse cases. Scoring likelihood and impact separately kept the ranking honest, so cheap, high-impact fixes such as MFA, per-user access checks, and server-side pricing come first, while rarer or lower-impact items wait. Every fix has a test that can be run, which turns the plan from advice into something that can be checked off.

Limitations: scores are judgment-based estimates for this assumed design, not measurements. A real review would confirm them against the actual code and hosting setup and revisit the model whenever a new feature, such as delivery or loyalty accounts, adds new data flows.
